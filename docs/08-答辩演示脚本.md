## 一、演示前 10 分钟准备

```powershell

# 前端（另一个终端）
```

## 三、分幕脚本

### 幕 0 · 开场（20 秒）

**操作**：停在首页，不要动。

**解说**：

> 这是一个前后端分离的轻量化 Web 小说平台。
> 前端 Vue 3 + Element Plus，后端 FastAPI + MySQL，一共 23 张表、83 个接口路径。
> 覆盖**读者、作者、管理员**三端的完整闭环，不是只有阅读功能的半成品。

---

### 幕 1 · 读者找书（60 秒）

**操作**

1. 首页往下滚，指一下「轮播 → 三书区 → 周点击榜 → 最近更新」
2. 点任意一本书进详情页
3. 点「开始阅读」

**应看到**：轮播右侧是**书籍自己的封面**；周点击榜有真实数据；详情页有简介、目录、书评。

**解说（挑重点说）**：

> 首页所有内容都来自数据库，包括轮播图——早期版本是写死 5 张图按序号轮播，
> 后来改成读 `book.cover`，**换封面只改数据库，不用改代码**。

---

### 幕 2 · 阅读与付费（150 秒）★ 重点

**2.1 免费试读（20 秒）**

1. 打开 `book/1`（山河剑歌）→ 点第 1 章
2. 正常显示正文

**解说**：

> 付费作品前 3 章免费，用于转化。这里能正常读。

**2.2 未购买拦截（40 秒）**

1. 用 `reader2` 登录
2. 直接点第 4 章

**应看到**：正文区变成购买卡片，显示价格。**正文一个字都没有。**

**解说**：

> 这里的关键不是前端遮住了，而是**后端只返回空正文**。
> 即使绕过前端直接请求接口 `GET /api/v1/chapters/4`，拿到的 `content` 也是空字符串，
> 只会带上 `locked=true` 和价格。
> 这是「服务端校验」，不是「前端隐藏」——两者安全性差一个数量级。

**2.3 购买（40 秒）**

1. 点「整本购买」
2. 余额减少，正文立刻解锁

**解说**：

> 购买用数据库事务 + 行锁，余额不足会返回 402。
> 重复点击不会重复扣费——`book_purchase` 上有唯一键 `(user_id, book_id)`。
> 整本购买会**扣掉已单独买过的章节金额**，不会让用户买两次。

**2.4 水印（30 秒，可选加分）**

1. 按 F12 → Network → 找到刚才那个章节请求 → 看 Response

**解说**：

> 已购用户拿到的正文里嵌了**零宽字符水印**，把 user_id 编成了不可见字符。
> 屏幕上完全看不出来，但复制文本会带走。
> 一旦付费内容外流，可以从文本里解出是哪个账号泄露的。
> 同时这个响应带 `Cache-Control: no-store`，防止被代理或 CDN 缓存。

### 幕 3 · 间贴（60 秒）

**操作**

1. 阅读页，鼠标移到某个段落 → 点右侧「+」
2. 发一条：`这一段写得真好`
3. 发一条：`想聊的可以加微信`
4. 发一条：`作者真是个骗子`

**应看到**：第 1 条正常显示；第 2 条**被拒绝**并提示命中违禁词；第 3 条能发出去。

**解说**：

> 间贴是「按段落」的评论，模仿的是刺猬猫的段评。
> 第 2 条被拦是因为命中广告类违禁词——注意，**改成「加-微-信」也拦得住**，
> 因为匹配前会把空白和分隔符剥掉再比对，这是防止绕过。
> 第 3 条能发出去但会进待审核队列，因为「骗子」是辱骂类，属于转人工级别。

**关键设计点（务必说）**：

> **章节是先审后发，间贴是先发后审。**
> 章节是正式内容，必须过审才让读者看到；
> 间贴如果每句都等审核，评论区会死掉，所以待审核状态照样展示，只有被驳回才隐藏。
> 同一个系统里两种策略，是因为两者的时效性要求不同。

### 幕 4 · 作者视角（120 秒）★ 重点

**操作**

1. 用 `author1` 登录 → 进作者中心
2. 找到《炼狱》，指状态列：**未提交**
3. 点「提交审核」→ 状态变**待审核**
4. 进「章节」→ 新增一章《第1章 试炼》，正文随便写 200 字
5. 退出登录，用读者身份打开 `book/28`

**应看到**：作者端有清晰的两列状态（审核状态、上架状态）；
新建的章节**前台目录里看不到**，直接访问章节地址也打不开。

**解说**：

> 这是我在原有设计上补的一块：**状态提醒**。
> 原来的设计只有「待审核/通过/驳回」，而且审核通过就等于上架，
> 作者完全不知道自己的书走到哪一步了。

> 现在拆成**两段流水线**：
> 第一段是内容审核（未提交 → 待审核 → 通过/未通过），
> 第二段是上架审核（未上架 → 申请中 → 已上架/未通过）。
> 也就是说 **审核通过 ≠ 已上架**，必须再申请一次。

**为什么这么设计（会被问）**：

> 因为内容合规和运营排期是两件事。
> 书可能已经过审了，但运营想等下周再上架；也可能上架后因为档期被下架，
> 但「已通过审核」这个状态要保留，不然作者要重审一遍。

**章节的演示点**：

> 新章节现在是「先审后发」：`audit_status=1` 时前台目录不显示，
> 直接访问章节 ID 也返回 3002 章节不存在。
> 只有管理员审核通过后才进目录。

### 幕 5 · 管理员视角（180 秒）★★ 三个杀手点

**5.1 审核并上架（60 秒）**

1. 用 `admin` 登录 → 后台 → 书籍管理
2. 搜索「炼狱」→ 点「通过」
3. 切回 `author1` → 刷新作者中心 → 看到**审核通过** → 出现「申请上架」按钮
4. 点「申请上架」→ 状态变**上架审核中**
5. 切回 admin → 点「上架」
6. 打开前台搜索「炼狱」→ **出现了**

**杀手点 ①（务必演示）**

在步骤 2 之后、步骤 5 之前，去前台搜「炼狱」——**搜不到**。

> 注意，这时候这本书**已经审核通过了**，但前台还是搜不到。
> 因为前台可见的条件是「审核通过 **并且** 已上架」。
> 这个判断统一收敛到模型的 `is_online` 属性里，
> 而不是散落在十几个地方各写一遍 if——之前就是散着写，改一次漏三处。

**5.2 通知（30 秒）**

1. 切回 `author1`
2. 看顶栏右上角 → **铃铛上有红点**
3. 点铃铛 → 消息中心

**应看到**：三条通知（审核未通过 / 审核通过 / 已上架），点进去能跳到对应页面。

**解说**：

> 审核结果不是让作者自己去刷，而是主动通知。
> 通知和状态变更在**同一个事务**里提交，不会出现「状态改了但没通知」。

**5.3 敏感词检测（40 秒）**

1. 后台 → 敏感词库
2. 在「在线检测框」输入：`加微信了解，骗子勿扰`
3. 点检测

**应看到**：拦截词：加微信；转人工词：骗子。

**解说**：

> 词库分两级：**block 直接拦截**、**review 转人工**。
> 如果全部拦截，误伤会很严重；如果全部放行，等于没有过滤。
> 演示数据只有 15 条词，真实部署要导入完整词表。

**5.4 举报处理（50 秒）**

1. 切到 `reader2`，在任意书评上点「举报」，选理由提交
2. 切到 admin → 后台 → 举报管理 → 看到待处理
3. 点「隐藏内容」

**应看到**：前台该评论消失。

**解说**：

> 举报要点：**同一个人对同一条内容只能举报一次**（数据库唯一键保证）；
> **不能举报自己发的内容**；隐藏内容会连带关闭这条内容的所有待处理举报，
> 避免管理员重复处理同一件事。
> 另外点赞、点踩、举报是**三个独立动作**，可以同时点赞又举报——
> 早期版本把它们做成三选一，语义上是错的。

### 幕 6 · 排行榜（60 秒）

**操作**

1. 打开 `/rank`，再点进「点击榜」
2. 切换「周榜 / 月榜 / 总榜」

**应看到**：三者的排名**不一样**。

**解说**：

> 总榜是累计点击，周榜是最近 7 天、月榜是最近 30 天。
> 原来只有一个累计字段，根本回答不了「本周最火的是哪本」。
> 所以加了 `book_daily_stat` 表按天记录，
> 用户点击、收藏、投喂时**双写**：累计字段 +1，当日流水 +1。

**诚实说明（主动讲，比被问出来好）**：

> 演示库里的历史流水是用脚本回填的模拟数据，因为种子数据只有累计值。
> 真实运行时是双写产生的——我可以现场点几本书，你会看到今日流水立刻变化。

### 幕 7 · 安全防护（60 秒，可选）

**7.1 UA 拦截**（在终端执行）

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "User-Agent: python-requests/2.31" http://127.0.0.1:8000/api/v1/books
```

**应看到**：`429`

**解说**：

> 只拦「UA 不含 Mozilla 且命中脚本特征」的请求。
> 用黑名单而不是白名单，是因为白名单会把浏览器插件、旧浏览器、App 内嵌 WebView
> 全挡在外面，误伤成本远高于漏放的收益。

**7.2 限流**（⚠️ **必须放在最后演示**）

连续在登录页输错 7 次密码 → 第 7 次返回 429。

> ⚠️ 这会把本机 IP 的登录额度用光（6 次/分钟），**之后 1 分钟内谁都登录不了**。
> 演示完如果还要继续，重启后端即可清空（限流状态在进程内存）。

**解说**：

> 分级限流：登录 6 次/分、章节正文 30 次/分、写操作 20 次/分、其它 150 次/分。
> 另外还有一层**按账号**的章节限流（40 章/分），
> 因为「买一本、脚本批量导出」这种行为用 IP 限流看不出来——频率不高但目标集中。

## 五、常见追问与标准答案

| # | 问题 | 回答要点 |
|---|---|---|
| 1 | 为什么用 FastAPI 不用 Django/Flask | 自动生成 OpenAPI 文档；Pydantic 做入参校验；依赖注入天然适合做权限；同步 ORM 写起来比异步直观 |
| 2 | 为什么不用 Redis | 单机部署，引入 Redis 只是多一个要维护的组件。限流与封禁状态放进程内存，代码里已注明「多实例需换 Redis」 |
| 3 | 密码怎么存 | PBKDF2-HMAC-SHA256，26 万次迭代，格式 `pbkdf2_sha256$iter$salt$hash`，日志里禁止出现密码 |
| 4 | JWT 怎么失效 | 无状态签名，靠 2 小时短期有效 + 数据库 `status` 字段兜底（禁用用户即使有 token 也拒绝） |
| 5 | 付费内容怎么防绕过 | 四层：服务端校验返回空正文、零宽水印溯源、`no-store` 禁缓存、账号级章节限流 + 审计日志 |
| 6 | 敏感词怎么防绕过 | 匹配前剥离空白与常见分隔符；词库在内存缓存 60 秒，后台改词立即失效 |
| 7 | 为什么章节和间贴审核策略不同 | 章节是正式内容必须把关；间贴时效性强，全审会杀死讨论，所以先发后审 |
| 8 | 周榜数据哪来的 | `book_daily_stat` 按天记录，点击/收藏/投喂双写；演示历史数据由脚本回填，已说明 |
| 9 | 为什么 `book` 表有冗余统计字段 | 列表页要按字数/章节数排序，实时聚合太慢；由 `recalc_stats()` 在同一事务里维护 |
| 10 | 并发下计数器会不会丢更新 | 用 `UPDATE ... SET count = count + 1` 原子自增，不做「先查后改」 |
| 11 | 为什么 uvicorn 只开 1 个 worker | 限流状态在进程内存，多 worker 会让额度翻倍，等于限流失效 |
| 12 | 越权怎么防 | 两层：`require_role` 依赖做角色校验；service 里 `_own_book()` 校验资源归属（返回 6001）|
| 13 | 怎么保证质量 | 61 个 pytest 用例，独立测试库，覆盖认证、审核状态机、付费、敏感词、限流 |
| 14 | 怎么部署 | 两套：Nginx + systemd（单机）、Docker Compose（含 MySQL）|
| 15 | 系统瓶颈在哪 | 单机内存态、无缓存层、搜索用 SQL LIKE（不是全文索引）；扩展方向见论文「局限与展望」|

## 六、翻车预案

| 情况 | 处理 |
|---|---|
| 后端 500 / 页面白屏 | 看后端终端报错；`Ctrl+C` 重启 uvicorn，数据在数据库不会丢 |
| 登录被 429 | 重启后端清空限流状态，或等 60 秒 |
| 演示数据被我点乱了 | 执行附录 B 的「一键重置」 |
| 搜「炼狱」搜不到 | 它可能已是上架状态；先看后台书籍管理里的状态 |
| 网络断了 | 全部素材本地化：图片在 `public/`，字体本地，`npm run dev` 不依赖外网 |
| 时间不够 | 直接讲「三个杀手点」，再补一句测试与部署 |
