> 版本：v1.0　编写日期：2026-11-26
> 目的：三个月后你还能看懂自己写的代码；答辩时能解释每一处为什么这么写。

## 1. 命名规范

### 1.1 后端（Python）

| 对象 | 规则 | 示例 |
|---|---|---|
| 模块/包 | 小写下划线 | `book_service.py`、`api/v1/` |
| 类 | 大驼峰 | `BookChapter`、`AuthService` |
| 函数/变量 | 小写下划线 | `get_book_detail`、`chapter_no` |
| 常量 | 全大写 | `TOKEN_EXPIRE_MINUTES` |
| Pydantic 模型 | 名词 + 用途后缀 | `BookCreate`、`BookDetailOut`、`BookQuery` |
| SQLAlchemy 模型 | 单数名词 | `Book`、`Comment` |
| 私有函数 | 前缀下划线 | `_build_rank_sql()` |

**布尔变量命名**：`is_` / `has_` / `can_` 开头，禁止 `flag`、`status2` 这类命名。

```python
is_collected = ...
has_update = ...
can_edit = ...
```

### 1.2 前端（Vue / JS）

| 对象 | 规则 | 示例 |
|---|---|---|
| 组件文件 | 大驼峰 | `BookCard.vue` |
| 普通 js 文件 | 小驼峰或小写下划线 | `request.js`、`format.js` |
| 组合式函数 | `use` 前缀 | `useBookList()` |
| ref 变量 | 小驼峰 | `const bookList = ref([])` |
| 常量 | 全大写 | `const PAGE_SIZE = 20` |
| CSS 类 | BEM 或语义化短横线 | `.book-card__title`、`.rank-item` |
| 事件 | `handle` + 动作 | `handleAddShelf`、`handlePageChange` |

### 1.3 数据库

见 [03-数据库设计说明书 §1](03-数据库设计说明书.md)。核心：表名单数、索引前缀 `uk_`/`idx_`/`fk_`。

## 2. 代码风格

### 2.1 后端

- 遵循 **PEP 8**，行宽 **100**（不是 79，中文注释多，太窄反而难读）。
- 使用 `ruff` 做 lint + format（比 black + flake8 + isort 三件套快且配置少）。

```ini
# pyproject.toml
[tool.ruff]
line-length = 100
target-version = "py311"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]
ignore = ["E501"]   # 行宽由 formatter 控制
```

- **所有函数必须有类型注解**，尤其是 service 层：

```python
def list_books(db: Session, query: BookQuery) -> tuple[list[Book], int]:
    ...
```

- 禁止 `from xxx import *`。
- 禁止在路由函数里写超过 15 行的业务逻辑 —— 超过就抽到 service。

### 2.2 前端

- 统一使用 **组合式 API + `<script setup>`**，不写 Options API。
- 缩进 2 空格；字符串优先单引号；必须加分号（团队统一即可，关键是别混用）。
- 组件内顺序固定：

```
<script setup>
  // 1. imports
  // 2. props / emits
  // 3. store
  // 4. ref / reactive
  // 5. computed
  // 6. 方法
  // 7. 生命周期
</script>

<template>...</template>

<style scoped>...</style>
```

- `props` 必须声明类型和默认值：

```js
const props = defineProps({
  book: { type: Object, required: true },
  size: { type: String, default: 'md' }
})
```

## 3. 注释与文档

### 3.1 什么必须写注释

| 必须注释 | 示例 |
|---|---|
| **为什么**这么做（而非做了什么） | `# 用原子自增而非先查后改，避免并发丢更新` |
| 业务规则 | `# 书架排序：置顶优先，其次收藏时间倒序` |
| 非直觉写法 | `# 这里用 subquery 是因为 MySQL 不支持 count 窗口函数` |
| 临时方案 | `# TODO(2026-12): P4 阶段替换为 FULLTEXT 查询` |

### 3.2 什么不要写

```python
# ❌ 废话注释
i += 1  # i 加 1

# ❌ 过期注释（比没有更糟）
# 返回书籍数量    ← 实际返回的是 (books, total)
```

### 3.3 函数文档字符串

service 层的公开函数必须有 docstring，写清「参数 + 返回 + 异常」：

```python
def create_chapter(db: Session, book_id: int, title: str, content: str) -> BookChapter:
    """新增章节并在同一事务内回写书籍统计字段。

    Args:
        db: 数据库会话（调用方负责 commit）。
        book_id: 目标书籍 ID。
        title: 章节标题。
        content: 正文纯文本。

    Returns:
        新建的 BookChapter 实例。

    Raises:
        BizError(3001): 书籍不存在。
        BizError(6001): 当前用户不是该书作者。
    """
```

## 4. Git 规范

### 4.1 分支模型

```
main        ← 只放能跑通的版本，答辩前打 tag
  └── dev   ← 日常开发主线
        ├── feature/auth
        ├── feature/book-list
        └── fix/reader-scroll
```

| 分支 | 用途 | 合并方式 |
|---|---|---|
| `main` | 稳定版，随时可演示 | 从 `dev` 合并 |
| `dev` | 开发主线 | — |
| `feature/*` | 单个功能 | 完成后合回 `dev` |
| `fix/*` | 修 bug | 完成后合回 `dev` |

> 一个人开发也要开分支。好处不是协作，而是**出问题时能快速回退**，且答辩时展示的提交历史更好看。

### 4.2 提交信息格式

```
<type>(<scope>): <中文简述>

[可选正文]
[可选脚注]
```

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 文档 |
| `style` | 格式（不影响逻辑） |
| `refactor` | 重构 |
| `test` | 测试 |
| `chore` | 构建/依赖/配置 |

**示例**

```
feat(book): 新增书库列表接口与筛选

- 支持 category_id / keyword / status / sort
- 分页默认 20 条
- 排序字段走对应索引

Closes #12
```

```
fix(reader): 修复切换章节后滚动位置未重置
```

### 4.3 提交前检查清单

- [ ] 代码能跑（`uvicorn` / `npm run dev` 无报错）
- [ ] 没有 `console.log` / `print()` 残留
- [ ] 没有把 `.env`、密码、密钥提交上去
- [ ] 改了接口 → 同步改了 `docs/04-接口文档.md`
- [ ] 改了表结构 → 同步改了 `db/schema.sql` 与 `docs/03`
- [ ] 在 `DEVLOG.md` 记了一笔

## 5. 依赖管理

### 5.1 后端

`requirements.txt` 固定版本（`==`），不用 `>=` 或 `latest`：

```
fastapi==0.115.6
uvicorn[standard]==0.34.0
SQLAlchemy==2.0.36
PyMySQL==1.1.1
pydantic==2.10.4
pydantic-settings==2.7.0
PyJWT==2.10.1
loguru==0.7.3
cryptography==44.0.0
```

> **为什么固定版本**：三个月后重装环境，`pip install fastapi` 可能装到不兼容的新版本，排查成本极高。

### 5.2 前端

`package.json` 提交 `package-lock.json`（或 `pnpm-lock.yaml`），保证可复现安装。

新增依赖前先问三个问题：

1. 能不能用现有依赖实现？
2. 这个包维护活跃吗（最近一年有提交）？
3. 体积多大（`bundlephobia.com` 查一下）？

## 6. 环境与配置

| 规则 | 说明 |
|---|---|
| `.env` 绝不入库 | 提交 `.env.example`，`.env` 写进 `.gitignore` |
| 配置集中读取 | 后端统一走 `app/core/config.py` 的 `settings`，禁止在业务代码里 `os.getenv` |
| 前端环境变量 | 必须以 `VITE_` 开头，如 `VITE_API_BASE` |
| 密钥生成 | `python -c "import secrets; print(secrets.token_urlsafe(32))"` |

## 7. 接口对齐流程（前后端并行时必守）

```
① 先改 docs/04-接口文档.md
        ↓
② 在 DEVLOG 记「为什么改」
        ↓
③ 后端改 schemas/ + 路由
   前端改 api/ 模块
        ↓
④ 联调（后端 /docs 里直接试）
        ↓
⑤ 双方都跑通 → 提交
```

**绝对禁止**：后端先偷偷改字段，前端跑起来发现 `undefined` 再回头查半天。

## 8. 调试约定

| 场景 | 做法 |
|---|---|
| 后端看 SQL | `echo=True` 临时打开 engine，**提交前必须关掉** |
| 后端看请求 | `http://localhost:8000/docs` 直接调，比 Postman 快 |
| 前端看接口 | DevTools Network，看 Request Payload 与 Response |
| 跨域问题 | 先确认 Vite 代理生效，而不是急着改后端 CORS |
| 状态不更新 | 先查是不是 `ref` 被解构丢了响应性 |
