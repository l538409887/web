## 1. 设计原则

| 编号 | 原则 | 说明 |
|---|---|---|
| D1 | 引擎与字符集 | 全部 `InnoDB` + `utf8mb4` + `utf8mb4_0900_ai_ci`，支持 emoji 与中文排序 |
| D2 | 主键 | 统一 `BIGINT UNSIGNED AUTO_INCREMENT`，避免后期分表主键溢出 |
| D3 | 时间 | 统一 `DATETIME`（非 `TIMESTAMP`，避免 2038 问题与时区隐式转换） |
| D4 | 布尔 | 用 `TINYINT(1)`，不用 `BOOL`（MySQL 中 `BOOL` 即 `TINYINT(1)` 别名） |
| D5 | 外键 | **物理外键保留**，用于保证引用完整性；删除策略按业务选择 `CASCADE` / `RESTRICT` |
| D6 | 命名 | 表名小写下划线，**单数**；外键列名 `xxx_id`；唯一索引 `uk_`，普通索引 `idx_`，外键 `fk_` |
| D7 | 冗余 | 允许**可控冗余**（字数字段、最新章字段），但必须写明回写规则 |
| D8 | 大字段 | 章节正文 `LONGTEXT` 单独存放于 `book_chapter`，**不参与**列表查询 |

> **为什么主键用 BIGINT 而不是 INT**：`book_chapter` 是全库唯一可能上千万行的表，INT 上限 21 亿虽够用，但保持全库主键类型一致可以减少后期 JOIN 的类型转换与迁移成本。

### 2.2 关系清单

| `sys_user` ↔ `book` | M:N | 通过 `book_vote` 表达投票，带月份维度 |

## 4. 表结构详述

### 4.1 `sys_user` 用户表

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|:--:|---|---|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `username` | VARCHAR(32) | 否 | — | 登录名，唯一，3~20 字符 |
| `password_hash` | VARCHAR(255) | 否 | — | `pbkdf2_sha256$迭代次数$salt$hash` |
| `nickname` | VARCHAR(32) | 否 | `''` | 昵称，空则回退 `username` |
| `email` | VARCHAR(128) | 是 | NULL | 邮箱（唯一，允许多个 NULL） |
| `avatar` | VARCHAR(255) | 否 | `''` | 头像 URL |
| `bio` | VARCHAR(255) | 否 | `''` | 个人简介 |
| `role` | ENUM | 否 | `reader` | `reader` / `author` / `admin` |
| `status` | TINYINT | 否 | 1 | 1 正常 / 0 禁用 |
| `last_login_at` | DATETIME | 是 | NULL | 最后登录时间 |
| `created_at` | DATETIME | 否 | NOW | 注册时间 |
| `updated_at` | DATETIME | 否 | NOW ON UPDATE | 更新时间 |

**索引**

| 名称 | 字段 | 类型 | 用途 |
|---|---|---|---|
| `uk_username` | `username` | 唯一 | 登录查询、注册查重 |
| `uk_email` | `email` | 唯一 | 邮箱查重 |
| `idx_role_status` | `role, status` | 普通 | 后台按角色/状态筛选 |

> **密码格式**：`pbkdf2_sha256$260000$<salt_hex>$<hash_hex>`
> 选 PBKDF2-HMAC-SHA256 而非 bcrypt 的原因：Python 标准库 `hashlib.pbkdf2_hmac` 直接支持，**零第三方依赖**，在 Python 3.14 环境下无需编译，且迭代 26 万次符合 OWASP 2023 对 PBKDF2-SHA256 的建议（≥ 600,000 次为更严标准，本项目取 260,000 次平衡登录耗时）。
> 若后续部署环境允许，可平滑切换到 bcrypt：哈希串前缀不同，校验时按前缀分派即可。

### 4.2 `book_category` 书籍分类表

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|:--:|---|---|
| `id` | INT UNSIGNED | 否 | 自增 | 主键 |
| `name` | VARCHAR(32) | 否 | — | 分类名，唯一 |
| `sort` | INT | 否 | 0 | 排序值，升序 |
| `created_at` | DATETIME | 否 | NOW | — |

> 分类**只有一级**。起点有二级分类，但二级分类会带来「导航树 + 递归查询 + 后台树形编辑」三块额外工作量，收益有限，故砍掉，改用标签做横向补充。

### 4.4 `book_tag` / `book_tag_rel`

| 表 | 字段 | 说明 |
|---|---|---|
| `book_tag` | `id` INT, `name` VARCHAR(32) 唯一, `created_at` | 标签字典 |
| `book_tag_rel` | `book_id` BIGINT, `tag_id` INT，联合主键 | 多对多关联，双向索引 |

> 用「标签表 + 关联表」而不是在 `book` 里存逗号分隔字符串，是为了避免 `FIND_IN_SET` 这类无法走索引的查询，也便于后台统计「哪些标签最热」。

### 4.5 `book_chapter` 章节表

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|:--:|---|---|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `book_id` | BIGINT UNSIGNED | 否 | — | FK，`ON DELETE CASCADE` |
| `chapter_no` | INT UNSIGNED | 否 | — | 书内序号，从 1 递增 |
| `title` | VARCHAR(200) | 否 | — | 章节标题（含「第 N 章」） |
| `content` | LONGTEXT | 否 | — | 正文，纯文本，`\n` 分段 |
| `word_count` | INT UNSIGNED | 否 | 0 | 本章字数 |
| `status` | TINYINT | 否 | 1 | 1 正常 / 0 屏蔽 |
| `created_at` / `updated_at` | DATETIME | 否 | NOW | — |

**索引**

| 名称 | 字段 | 类型 | 用途 |
|---|---|---|---|
| `uk_book_no` | `book_id, chapter_no` | 唯一 | 保证书内章节号不重复；同时是**目录查询的覆盖索引** |
| `idx_book_status` | `book_id, status` | 普通 | 按状态过滤 |

> **为什么正文用纯文本而不是 HTML**：
> ① 防 XSS —— 前端按 `\n` 切分渲染 `<p>`，作者输入的 `<script>` 只会被当作文本；
> ② 存储省 30%~50%；
> ③ 便于统计字数（`CHAR_LENGTH`）。
> 代价是丢失富文本排版，但小说正文本来就只需要段落。

### 4.6 `user_bookshelf` 书架表

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|:--:|---|---|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `user_id` | BIGINT UNSIGNED | 否 | — | FK，`ON DELETE CASCADE` |
| `book_id` | BIGINT UNSIGNED | 否 | — | FK，`ON DELETE CASCADE` |
| `is_top` | TINYINT | 否 | 0 | 1 = 置顶 |
| `created_at` | DATETIME | 否 | NOW | 收藏时间 |

**索引**：`uk_user_book (user_id, book_id)` 唯一 —— 从数据库层面杜绝重复收藏；`idx_user_top (user_id, is_top, created_at)` 支撑书架列表排序。

### 4.7 `reading_history` 阅读进度表

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|:--:|---|---|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `user_id` | BIGINT UNSIGNED | 否 | — | FK |
| `book_id` | BIGINT UNSIGNED | 否 | — | FK |
| `chapter_id` | BIGINT UNSIGNED | 否 | — | 最后阅读章节 |
| `chapter_no` | INT UNSIGNED | 否 | 0 | **冗余** 章节序号，避免展示时 JOIN |
| `progress` | TINYINT UNSIGNED | 否 | 0 | 章内进度 0~100 |
| `read_count` | INT UNSIGNED | 否 | 1 | 累计阅读次数 |
| `created_at` / `updated_at` | DATETIME | 否 | NOW | — |

**索引**：`uk_user_book (user_id, book_id)` 唯一 —— 支撑 `INSERT ... ON DUPLICATE KEY UPDATE` 的 Upsert 语义；`idx_user_time (user_id, updated_at)` 支撑「最近阅读」倒序。

> **关键设计：一张表只存一行（Upsert），而不是流水账。**
> 若做成流水，用户读 100 章就产生 100 行，且「读到哪」需要 `ORDER BY ... LIMIT 1`。
> 改成「每用户每书一行」后，取进度是一次主键级查找，写入是 `INSERT ... ON DUPLICATE KEY UPDATE`。
> 代价是丢失「阅读足迹」明细 —— 毕设不需要，论文中作为权衡说明。

### 4.8 `book_comment` 评论表

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|:--:|---|---|
| `id` | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| `book_id` | BIGINT UNSIGNED | 否 | — | FK |
| `chapter_id` | BIGINT UNSIGNED | 是 | NULL | **NULL = 书评；非 NULL = 章评** |
| `user_id` | BIGINT UNSIGNED | 否 | — | FK |
| `parent_id` | BIGINT UNSIGNED | 是 | NULL | 父评论；NULL = 主楼 |
| `content` | VARCHAR(500) | 否 | — | 内容 1~500 字 |
| `like_count` | INT UNSIGNED | 否 | 0 | 点赞数 |
| `status` | TINYINT | 否 | 1 | 1 正常 / 0 待审 / 2 已隐藏 |
| `created_at` | DATETIME | 否 | NOW | — |

**索引**：`idx_book_list (book_id, chapter_id, status, created_at)` —— 覆盖「某书/某章的正常评论按时间倒序」这一最高频查询。

> **为何书评与章评共用一张表**：两者字段完全一致，只差 `chapter_id` 是否为空。分两张表会导致「书评区含章评」这类混合查询变复杂，且代码翻倍。用可空外键区分，简单且可索引。

> **为何 `parent_id` 不建自引用外键**：逻辑删除（`status=2`）下物理行永远存在，外键不会断裂；但自引用外键会让「删除主楼是否级联删子回复」变得暧昧，且 `ON DELETE CASCADE` 会物理删行、与逻辑删除语义冲突。故只建 `idx_parent` 索引，删除主楼时由应用层在同一事务内把子回复一并置 `status=2`。

### 4.9 `book_vote` 投票表（P3 可选）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED | 主键 |
| `user_id` / `book_id` | BIGINT UNSIGNED | FK |
| `vote_type` | TINYINT | 1 推荐票 / 2 月票 |
| `vote_month` | CHAR(7) | `YYYY-MM` |
| `created_at` | DATETIME | — |

**索引**：`uk_user_book_type_month (user_id, book_id, vote_type, vote_month)` —— 保证「同一用户对同一本书、同一种票、同一月份只能投一次」；`idx_book_month (book_id, vote_month, vote_type)` —— 支撑月票榜聚合。

## 5. 冗余字段与回写规则

这是本设计里**最需要讲清楚**的一点，也是答辩容易被问的地方。

| 冗余字段 | 真实来源 | 回写时机 | 为什么值得冗余 |
|---|---|---|---|
| `book.word_count` | `SUM(book_chapter.word_count)` | 新增/删除/修改章节后 | 书库列表要展示字数，否则每行都要子查询聚合 |
| `book.chapter_count` | `COUNT(book_chapter)` | 同上 | 同上 |
| `book.last_chapter_id` | `MAX(chapter_no)` | 同上 | 「最新章节」跳转必备 |
| `book.last_chapter_title` | 同上 | 同上 | 首页/书架展示，避免 JOIN |
| `book.last_update_at` | `MAX(chapter.created_at)` | 同上 | 「最近更新」排序依赖它，必须可索引 |
| `book.click_count` | 累加 | 详情页访问时 `+1` | 榜单排序需要索引，不能实时聚合 |
| `reading_history.chapter_no` | `book_chapter.chapter_no` | 上报进度时 | 书架展示「读到第 N 章」免 JOIN |

**一致性保证**：以上回写全部放在**同一数据库事务**内完成，示例：

```python
async def create_chapter(db, book_id, title, content):
    async with db.begin():                       # 开启事务
        chapter = BookChapter(book_id=book_id, ...)
        db.add(chapter)
        await db.flush()                         # 拿到 chapter.id
        await db.execute(
            update(Book).where(Book.id == book_id).values(
                chapter_count=Book.chapter_count + 1,
                word_count=Book.word_count + len(content),
                last_chapter_id=chapter.id,
                last_chapter_title=title,
                last_update_at=func.now(),
            )
        )
```

> 若追求绝对一致，可改为「触发器」或「定时重算任务」。毕设选择**应用层事务回写**，理由：逻辑集中、可测试、便于在论文中描述。

> **章节号并发生成**：`chapter_no = MAX(chapter_no) + 1` 在并发下可能撞号。`uk_book_no (book_id, chapter_no)` 唯一索引作为兜底——插入冲突时捕获异常重试一次。毕设单用户不会触发，但论文里说明这条可体现对并发的思考。

## 7. 容量与性能估算

| 表 | 单行估算 | 1 万章节时 | 说明 |
|---|---|---|---|
| `book_chapter` | ≈ 3 KB（正文 3000 字） | ≈ 30 MB | 万级章节对 MySQL 毫无压力 |
| `book` | ≈ 1 KB | 百级 → < 1 MB | — |
| `book_comment` | ≈ 0.5 KB | 万级 → 5 MB | — |
| 全库 | — | **< 100 MB** | 单机 MySQL 完全够用 |

**结论**：本项目数据量级远未触及 MySQL 单表瓶颈，不需要分库分表、读写分离或缓存层。论文「性能优化」章节应聚焦在**索引与查询语句**上，而不是架构层面，否则会显得脱离实际。
