## 1. 为什么要专门设计日志

毕设系统出问题时，最常见的三种情况：

1. 前端报「网络异常」，但不知道后端到底有没有收到请求。
2. 后端 500，但控制台一闪而过，重启后啥也没留下。
3. 用户说「我明明收藏了」，数据库里却没有——不知道是没点、没提交，还是提交失败回滚了。

日志要能回答这三个问题。**日志不是 `print` 的替代品，是运行现场的黑匣子。**

---

## 2. 日志分级与使用场景

采用 Python 标准分级（Loguru 同名）：

| 级别 | 用在哪 | 举例 | 生产是否输出 |
|---|---|---|:--:|
| `DEBUG` | 开发期细节 | SQL 参数、缓存命中、分支走向 | ❌ |
| `INFO` | 正常业务里程碑 | 用户登录、发布章节、创建订单式操作 | ✅ |
| `WARNING` | 可恢复的异常 | 登录失败、重复收藏、参数越界被截断 | ✅ |
| `ERROR` | 业务失败但服务存活 | 数据库操作失败、第三方调用失败 | ✅ |
| `CRITICAL` | 服务不可用 | 启动时连不上数据库 | ✅ |

**判断口诀**：
- 「这条日志每天都在刷」→ `DEBUG`
- 「出事了想回看」→ `INFO`
- 「不太对但还能跑」→ `WARNING`
- 「这条出现了说明有 bug」→ `ERROR`

## 3. 日志文件划分

```
backend/logs/
├── app.log         # 全量（INFO 及以上），按天轮转
├── error.log       # 仅 ERROR / CRITICAL，带完整堆栈，按天轮转
├── access.log      # 每条 HTTP 请求一行（方法/路径/状态/耗时）
└── business.log    # 关键业务动作（登录、发布、审核、删除）
```

| 文件 | 保留 | 单个上限 | 格式 |
|---|---|---|---|
| `app.log` | 30 天 | 50 MB | 结构化文本 |
| `error.log` | 90 天 | 50 MB | 含堆栈 |
| `access.log` | 30 天 | 50 MB | 一行一条（类 Nginx） |
| `business.log` | 180 天 | 20 MB | 便于审计 |

> 为什么 `error.log` 保留更久：答辩前一周出的 bug，可能要到答辩当天才复现，堆栈是唯一线索。

## 4. 日志格式

### 4.1 `app.log` / `error.log`

```
2026-11-26 11:20:31.482 | INFO     | 3f8a1c2e | app.api.v1.books:list_books:42 | 书籍列表查询 category=2 sort=click page=1 命中12条 耗时23ms
 └──────┬──────┘ └─┬──┘ └──┬───┘   └──────────┬──────────┘  └────────────┬─────────┘
       时间        级别   trace_id            模块:函数:行号              消息
```

格式模板：

```python
LOG_FORMAT = (
    "{time:YYYY-MM-DD HH:mm:ss.SSS} | {level: <8} | {extra[trace_id]} | "
    "{name}:{function}:{line} | {message}"
)
```

### 4.2 `access.log`

```
2026-11-26 11:20:31 | 127.0.0.1 | user=6  | GET     /api/v1/books?page=1       | 200 |  23ms
       时间           客户端IP     用户       方法    路径                      状态   耗时
```

### 4.3 `business.log`

```
2026-11-26 11:20:31 | LOGIN    | user=6   | username=reader1  ip=127.0.0.1
2026-11-26 11:25:02 | SHELF_ADD| user=6   | book=1
2026-11-26 11:31:44 | CHAPTER_PUBLISH | user=2 | book=1 chapter=43 words=820
```

> 业务日志用**动作码**（`LOGIN`/`SHELF_ADD`/`CHAPTER_PUBLISH`）而不是中文句子，便于 grep 与统计。

## 5. trace_id：把所有日志串起来

### 5.1 机制

每个请求进入时生成一个 8 位短 ID，写入：

1. 日志的 `extra[trace_id]` 字段；
2. 响应体的 `trace_id`；
3. 响应头 `X-Trace-Id`。

```python
# app/core/logger.py
from contextvars import ContextVar
import uuid

trace_id_ctx: ContextVar[str] = ContextVar("trace_id", default="-")

def new_trace_id() -> str:
    tid = uuid.uuid4().hex[:8]
    trace_id_ctx.set(tid)
    return tid
```

```python
# main.py 中间件
@app.middleware("http")
async def trace_middleware(request: Request, call_next):
    tid = new_trace_id()
    request.state.trace_id = tid
    start = time.perf_counter()
    response = await call_next(request)
    cost = (time.perf_counter() - start) * 1000
    response.headers["X-Trace-Id"] = tid
    logger.bind(trace_id=tid).info(
        f"{request.method} {request.url.path} -> {response.status_code} {cost:.0f}ms"
    )
    return response
```

### 5.2 价值

前端弹窗提示「服务器错误（trace: 3f8a1c2e）」时，直接：

```bash
grep "3f8a1c2e" backend/logs/*.log
```

三条日志（请求行、业务行、异常堆栈）会一起出来，**不需要靠时间戳猜**。

## 6. 请求日志中间件

### 6.1 记录内容

| 字段 | 示例 | 说明 |
|---|---|---|
| 时间 | `2026-11-26 11:20:31` | — |
| 客户端 IP | `127.0.0.1` | 取 `X-Real-IP` → `X-Forwarded-For` → `request.client.host` |
| 用户 | `user=6` 或 `user=-` | 从 Token 解析，未登录为 `-` |
| 方法 | `GET` | — |
| 路径 | `/api/v1/books` | **不含 query string**（避免日志爆炸） |
| 状态 | `200` | — |
| 耗时 | `23ms` | `perf_counter` 差值 |

### 6.2 慢请求告警

```python
if cost > 500:
    logger.warning(f"SLOW {request.method} {request.url.path} {cost:.0f}ms")
```

> 500ms 是本地开发的宽松阈值。论文里写「超过 500ms 记录 WARNING，用于定位索引缺失」。

### 6.3 绝不记录的内容

| 禁止 | 原因 |
|---|---|
| 请求体全量 | 含密码、正文，体积大且涉隐私 |
| `Authorization` 头 | Token 泄露等于账号泄露 |
| 密码明文 | 常识 |
| 完整 `content` 正文 | 单章上万字，日志会爆 |

**允许的替代做法**：只记长度或摘要。

```python
logger.info(f"chapter_publish book={bid} words={len(content)}")
```

## 7. 脱敏规则

写一个统一的辅助函数，所有日志输出前过一遍：

```python
SENSITIVE_KEYS = {"password", "password_hash", "old_password", "new_password", "token", "authorization"}

def mask(data: dict) -> dict:
    return {k: ("***" if k.lower() in SENSITIVE_KEYS else v) for k, v in data.items()}
```

| 字段 | 脱敏方式 |
|---|---|
| 密码 | `***` |
| Token | 只保留前 6 位 + `...` |
| 手机号 | `138****5678` |
| 邮箱 | `a***@b.com` |

## 8. 业务日志清单（必须记）

| 动作码 | 触发时机 | 关键字段 |
|---|---|---|
| `REGISTER` | 注册成功 | `user_id, username, ip` |
| `LOGIN` | 登录成功 | `user_id, username, ip` |
| `LOGIN_FAIL` | 登录失败 | `username, ip, reason`（**不记密码**） |
| `LOGOUT` | 退出登录 | `user_id` |
| `PASSWORD_CHANGE` | 修改密码 | `user_id` |
| `SHELF_ADD` / `SHELF_REMOVE` | 书架变更 | `user_id, book_id` |
| `COMMENT_CREATE` / `COMMENT_DELETE` | 评论变更 | `user_id, comment_id, book_id` |
| `CHAPTER_PUBLISH` | 发布章节 | `user_id, book_id, chapter_id, words` |
| `BOOK_AUDIT` | 上下架 / 审核 | `admin_id, book_id, from, to` |
| `USER_STATUS_CHANGE` | 禁用 / 改角色 | `admin_id, target_id, from, to` |

> 这些日志在论文里可以写成「审计日志」一节：**谁、在什么时候、对什么、做了什么**。这是管理系统类毕设的加分点。

## 9. 异常日志

### 9.1 分级处理

```python
@app.exception_handler(BizError)
async def biz_error_handler(request, exc: BizError):
    # 业务异常是「预期内」的，记 WARNING，不打堆栈
    logger.bind(trace_id=request.state.trace_id).warning(f"BizError {exc.code}: {exc.message}")
    return fail(exc.code, exc.message)


@app.exception_handler(Exception)
async def unhandled_handler(request, exc: Exception):
    # 未捕获异常是「预期外」的，记 ERROR + 堆栈
    logger.bind(trace_id=request.state.trace_id).opt(exception=exc).error("未捕获异常")
    return fail(9999, "服务器内部错误")
```

### 9.2 堆栈只进日志，不进响应

```python
# ❌ 绝对不要
return JSONResponse({"code": 9999, "message": str(exc), "trace": traceback.format_exc()})

# ✅ 正确
return fail(9999, "服务器内部错误")   # 前端只看到这句话 + trace_id
```

> 答辩时这句可以讲成「防止通过错误信息探测系统内部结构」。

## 10. 配置示例

```python
# app/core/logger.py
import sys
from loguru import logger
from app.core.config import settings

def setup_logger():
    logger.remove()

    # 控制台：开发期彩色、DEBUG；生产只 INFO
    logger.add(
        sys.stderr,
        level="DEBUG" if settings.APP_ENV == "dev" else "INFO",
        colorize=True,
        format=LOG_FORMAT,
    )

    common = dict(
        rotation="00:00",            # 每天 0 点切分
        retention="30 days",
        encoding="utf-8",
        enqueue=True,                # 多进程安全
        backtrace=True,
        diagnose=False,              # 生产关闭变量打印，防泄露
        format=LOG_FORMAT,
    )

    logger.add("logs/app.log",      level="INFO",  **common)
    logger.add("logs/error.log",    level="ERROR", **common)
    logger.add("logs/business.log", level="INFO",  filter=lambda r: "business" in r["extra"],
               rotation="00:00", retention="180 days", encoding="utf-8", enqueue=True)

    return logger
```

## 11. 前端日志（简化版）

前端不做完整日志系统，只做**错误捕获 + 本地留存**：

```js
// main.js
app.config.errorHandler = (err, instance, info) => {
  console.error('[Vue Error]', err, info)
  const logs = JSON.parse(localStorage.getItem('novel_platform_error_logs') || '[]')
  logs.unshift({ time: new Date().toISOString(), message: err.message, info })
  localStorage.setItem('novel_platform_error_logs', JSON.stringify(logs.slice(0, 20)))  // 只留 20 条
}
```

用途：答辩现场如果某个页面白屏，打开 DevTools 能看到最近的错误，而不是靠回忆。

> 不上报后端：需要额外接口与鉴权，收益低。

## 12. 日志排查示例

### 场景：用户反馈「收藏失败」

```bash
# 1. 从用户看到的提示里拿到 trace
grep "3f8a1c2e" backend/logs/app.log

# 输出
2026-11-26 11:25:02 | INFO  | 3f8a1c2e | trace_middleware | POST /api/v1/bookshelf -> 400 15ms
2026-11-26 11:25:02 | WARN  | 3f8a1c2e | shelf_service:add:31 | BizError 4001: 该书籍已在书架中

# 2. 结论：不是 bug，是重复收藏，前端应按幂等处理
```

### 场景：接口突然变慢

```bash
# 找最慢的 10 条
grep "SLOW" backend/logs/app.log | tail -10

# 输出
2026-11-26 14:02:11 | WARNING | a1b2c3d4 | 慢请求 GET /api/v1/books 780ms
```

再去 `app.log` 里看同 trace 的 SQL 日志（DEBUG 级别），基本能定位到缺索引。
